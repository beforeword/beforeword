# beforeword · interrupted evaluations without blind retries

[Русский](CHECKPOINTS.ru.md) · [Runner and review](README.md)

`checkpoint.py` is an optional companion to `run.py`. It records the planned request before calling a provider and saves each returned record in a local SQLite database. It does not remove ChatGPT limits, purchase credits, or establish that a request was billed. Real calls still require `--execute` and the provider's separately configured credentials.

## Preview, execute, resume

From the repository root, preview two cases without requests or checkpoint writes:

```bash
python3 evaluations/multi-provider/checkpoint.py --model PROVIDER/MODEL
```

Replace `PROVIDER/MODEL` with an actual supported route. Explicitly start a potentially billed run:

```bash
python3 evaluations/multi-provider/checkpoint.py --execute --model PROVIDER/MODEL --state results/baseline.sqlite3
```

After an interruption, repeat the same options and add `--resume`:

```bash
python3 evaluations/multi-provider/checkpoint.py --execute --resume --model PROVIDER/MODEL --state results/baseline.sqlite3
```

The default is two cases per route, not the full suite. `--all` selects all cases; `--limit N` selects the first N. `--dataset`, `--instruction-file`, `--timeout`, `--max-tokens`, and optional `--temperature` work as in the original runner. An odd or arbitrary limit can leave an a/b pair incomplete; it is not a complete paired evaluation.

For 1.3.6, supply its exact instruction and language-specific dataset to all invocations of that run:

```bash
python3 evaluations/multi-provider/checkpoint.py \
  --dataset evaluations/instruction-1.3.6/samples.ru.jsonl \
  --instruction-file evaluations/instruction-1.3.6/core.ru.txt \
  --model PROVIDER/MODEL
```

Add `--execute --state results/candidate-ru.sqlite3` only to authorize real calls. Use separate checkpoints for baseline, 1.3.5, and 1.3.6; the same cases and generation settings are needed for a meaningful comparison. These commands are instructions, not reports that such comparisons have occurred.

## What gets resumed

| Stored state | Meaning in this program | On resume |
| --- | --- | --- |
| `pending` | No durable dispatch marker yet | Eligible for a first attempt |
| `started` | Marker committed, but no terminal record | Never retried automatically; outcome unresolved |
| `response_received` | Supported nonblank text was recorded | Skipped |
| `request_failed` | The runner recorded an exception or unsupported response | Skipped; not proof of no charge |

The queue stops at its first recorded failure, including quota or authentication errors. A subsequent explicit resume can attempt the still-pending cases; it does not retry the failed case. A crash after recording `started` but before dispatch is also conservatively unresolved. This trades some missed requests for avoiding blind duplicate attempts.

SQLite commits each start marker before the call and each outcome afterwards. A separate SQLite transaction excludes another collector using the same canonical checkpoint path; its lock is released when the process exits. Use local storage with working SQLite locking, not a synchronised/network filesystem. Keep the database and lock files in place while any collector is running. Copies of the database are independent and do not share a lock.

The full plan includes exact messages, criteria, instruction, selected cases/models, generation options, dataset checksum, and both collector source checksums. A changed plan or missing/corrupted request row stops resumption before calls. Checksums detect inconsistencies, not authenticity or tamper-proof provenance. Provider deployments and unspecified server defaults can still change between invocations.

Both runners now explicitly request `num_retries=0` from LiteLLM and record that option. This is not a guarantee about retries inside a gateway/provider, charges, delivery, or exactly-once external execution. No automatic switch to another model, purchase, or retry of an uncertain request is added.

## Inspect and export without model calls

```bash
python3 evaluations/multi-provider/checkpoint.py --state results/baseline.sqlite3 --status
python3 evaluations/multi-provider/checkpoint.py --state results/baseline.sqlite3 --export-jsonl results/baseline.jsonl
```

Export writes a **new** JSONL file and `baseline.jsonl.manifest.json`; it refuses existing destinations. Only terminal records enter JSONL, in planned order, preserving the exact response strings. The mandatory companion manifest records planned, pending, unresolved, failed, and received counts. Keep it with the results: a subset is not a completed benchmark. An export with no terminal results is empty and cannot yet be scored.

The nonempty JSONL is compatible with `score.py`. Its review template still needs independent human judgments; no verdicts are generated by checkpoints. Unresolved attempts are not converted into invented provider failures, successes, or passing scores. An earlier `run.py` JSONL cannot be resumed by this tool: no prior pre-dispatch markers exist for it.

Checkpoints contain prompts, instructions and outputs. Do not commit private runs. `/results/` and SQLite working files are ignored by Git, but this does not protect files uploaded elsewhere or override explicit `git add -f`.

## Offline tests

```bash
python3 -B evaluations/multi-provider/test_runner_contract.py
python3 -B evaluations/multi-provider/test_checkpoint.py
python3 -B -O evaluations/multi-provider/test_runner_contract.py
python3 -B -O evaluations/multi-provider/test_checkpoint.py
```

Tests use synthetic responses, process interruption and local files. They cover text preservation, defensive request copies, explicit retry parameters, validation, resumption, locking, changed plans, corrupt state, and coverage exports. Passing them is not a result for any real model, an installation check, or a billing audit.

Implementation references: [Python text input](https://docs.python.org/3.12/library/functions.html#open), [SQLite transactions](https://www.sqlite.org/lang_transaction.html), [LiteLLM retry option](https://docs.litellm.ai/docs/completion/reliable_completions).
